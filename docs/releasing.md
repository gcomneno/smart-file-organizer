# Release procedure

GitHub Releases is the supported distribution channel.

Each release contains one pure-Python wheel, one source distribution, and a
`SHA256SUMS` file covering both artifacts. The release workflow runs only for a
tag named `v<package-version>`; the tag and `project.version` must match.

Release integrity uses distinct, complementary evidence:

- reproducible build evidence: the workflow performs repeated deterministic
  builds with the same release inputs and requires byte-for-byte matching wheel
  and source distributions;
- `SHA256SUMS`: an independent digest list that remains downloadable and
  locally verifiable;
- GitHub Immutable Releases: an external repository setting that protects
  release assets and the associated tag after publication for releases created
  after the setting is enabled; historical releases are not made retroactively
  immutable;
- automatic immutable-release attestation: generated by GitHub for immutable
  releases, binding the release, tag, commit, and release assets;
- explicit build provenance: generated by `actions/attest` in the release
  workflow, tying built artifact digests to the GitHub Actions build context and
  workflow. This complements, but does not replace, the immutable-release
  attestation or `SHA256SUMS`.

## Prepare and verify

Run formatting, lint, type checking, the complete test suite on Python 3.11 and
3.12, the reproducible build, and installed-wheel smoke tests before merging a
release preparation pull request.

The build script performs two independent builds using the commit timestamp as
`SOURCE_DATE_EPOCH`. Both wheel and source distribution must compare
byte-for-byte.

## Publish

For Immutable Releases rollout, use this operator order:

1. Merge the repository-side release compatibility change.
2. Capture evidence of the current Immutable Releases repository setting.
3. Enable Immutable Releases in the GitHub repository settings.
4. Capture evidence of the enabled setting.
5. Only then create the next real release tag.
6. Verify that release.

Actual immutability and attestations for the first future immutable release
cannot be validated before that real release exists.

After merging a reviewed release preparation into `main`, create and push an
annotated tag matching the package version. For package version `X.Y.Z`, use
the tag `vX.Y.Z`.
The tag starts `.github/workflows/release.yml`, which rebuilds, verifies, smoke
tests, attests the release artifacts, creates a draft GitHub Release, uploads
the wheel, source distribution, and `SHA256SUMS`, validates that the draft
contains exactly those uploaded asset names, and only then publishes the draft.
Uploads do not use clobbering.

If upload or draft asset validation fails, the release remains a draft and is
not published. The workflow does not automatically clobber existing assets or
perform destructive cleanup; manually inspect and clean up the draft before
retrying.

## Verify downloaded artifacts

Download the wheel, source distribution, and `SHA256SUMS` into one empty
directory, then run:

~~~bash
sha256sum --check SHA256SUMS
~~~

For the first real release after Immutable Releases is enabled, verify the
GitHub release attestation, each downloaded asset, and the explicit build
provenance:

~~~bash
gh release verify vX.Y.Z -R gcomneno/smart-file-organizer
gh release verify-asset vX.Y.Z PATH -R gcomneno/smart-file-organizer
sha256sum --check SHA256SUMS
gh attestation verify PATH -R gcomneno/smart-file-organizer \
    --source-ref refs/tags/vX.Y.Z
~~~

A tag/version mismatch, non-reproducible build, checksum mismatch, failed smoke
test, failed attestation generation, draft asset mismatch, or existing release
with the same tag stops publication. Artifacts are not silently replaced.
